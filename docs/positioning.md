# 产品定位（v0.1 草案）

> 状态：定位与前端形态已定，其余待验证。用于统一后续产品与架构决策。
> 关联文档：[领域解耦清单](./domain-decoupling.md)、[开源发布检查清单](./open-source-release.md)、[开发清单](./development-checklist.md)。

## 0. 结论摘要

- 产品定位不是"智能客服系统"，而是**可私有化部署的对话式 Agent 运营平台**；客服是首个场景包，不是产品边界。
- 首要客户不是中大型企业，也不是纯小白 SME，而是**能自己跑 Docker 的技术型团队**。
- 商业化路径是**开源 + 企业版**，先私有化交付，SaaS 后置。
- 近期架构选择**单实例单租户**，只预留 `tenant_id` 字段，不做租户隔离逻辑。
- 第二个场景包选 **IT Helpdesk**，用真实场景倒逼内核抽象。
- 对外叙事原则：**卖场景，不卖引擎**。

## 1. 一句话定位

> 面向技术型团队的对话式 Agent 运营平台：把多意图路由、知识库、工具调用、跨轮记忆和全链路追踪装进一个可私有化部署的管理台，并内置客服/售后场景包。

面向客户的表达可以更短：

> 一套能部署在自己机房的 AI 客服与业务助手平台，答得上、查得到、接得住、可追溯。

## 2. 为什么不是"客服系统"

现有代码的能力分布已经说明问题：

| 已经是平台能力（与客服无关） | 客服耦合点 |
|---|---|
| 多意图路由与串行分发（`agents/router_agent.py`、`agents/orchestrator.py`） | 客户/人员双表与 `Session.user_id` 外键 |
| 代码 Agent + DB 动态 Agent 混合注册（`agents/registry.py`） | `tickets`、`canned_scripts` 两张表 |
| 记忆召回 + 多知识库 RAG + token 预算（`core/context_engineer.py`） | 订单/退款/物流/工单工具（`tools/custom/`） |
| MCP 与自定义工具管理（`tools/mcp_loader.py`、`api/v1/admin.py`） | 客服提示词与工单/咨询后台页面 |
| 全链路追踪与运营台（`core/tracing.py`、`request_traces`） | 固定话术匹配引擎与种子内容 |

结论：**内核接近干净，领域耦合集中在数据层、工具层和少量页面**。这决定了平台化是一次可控的"归位"，不需要重写引擎。

## 3. 目标客户

### 3.1 理想客户（ICP）

| 维度 | 描述 |
|---|---|
| 规模 | 50–1000 人，有研发或运维能力 |
| 角色 | 企业内部数字化团队、IT 部门、中小软件公司 |
| 现状 | 已有知识库/工单/CRM，但缺少统一的 AI 对话入口 |
| 诉求 | 数据不出内网、能接内部系统、效果可观测、成本可控 |
| 决策 | 技术负责人可拍板试用，1–2 周能完成部署验证 |

### 3.2 反 ICP（暂不服务）

- 没有技术团队、要求开箱即用 SaaS 的小微企业。
- 需要复杂 BPM/审批流定制的客户。
- 只接受一次性买断、拒绝年度授权与支持的客户。
- 要求"零代码搭建任意 Agent"的通用平台型客户。

## 4. 价值主张

1. **场景价值**：多意图识别、知识 + 工具混合应答、跨轮记忆、转人工兜底。
2. **运营价值**：每轮对话可追踪（路由、工具、RAG、记忆、耗时），知识库与话术可后台维护。
3. **部署价值**：私有化、数据不出内网、可接内网 MCP 服务与内部系统。
4. **迁移价值**：场景包可替换，同一套运行时支撑客服、IT Helpdesk、内部知识助手。

## 5. 产品结构

```
交付层   私有化部署（默认）   |   托管 SaaS（后续）   |   开源社区版
场景包   客服/售后包（首发）  |   IT Helpdesk（第二个）|   自定义包
平台层   Agent 运行时：路由 / 上下文工程 / 记忆 / 知识 / 工具 / 会话 / 链路 / 权限
```

产品页面按能力组织，而不是按客服业务组织：
- 平台级：Agent、知识库、自定义工具、MCP 服务、记忆、会话、链路、路由分发器
- 场景包级：工单、咨询记录、应答模板（当前叫"固定话术"）

### 5.1 前端形态（已定）

最终形态是**一个管理端 SPA + 一个聊天挂件**，不再保留两个独立网站。

| 项 | 决策 |
|---|---|
| 管理端 | 唯一的管理 SPA，承载运营台全部功能 |
| 聊天端 | 不做独立网站：v0.1 保留轻量应用，v0.2 输出可嵌入挂件（优先 iframe，按需 Web Component） |
| 代码组织 | npm workspaces 单仓多包，共享 http / auth / SSE / types；两套 token key 保持隔离 |
| 部署 | 一个 Nginx：`/` 聊天、`/admin/` 管理端、`/api/` 反代后端 |
| 明确不做 | 把聊天合并进管理端 SPA、微前端、v0.1 做 Web Component |

理由：聊天是渠道而不是产品本体，未来还要接企微/钉钉/开放 API；管理端才是运营核心。共享包消灭重复代码，挂件化让聊天可嵌入任意客户网站。

## 6. 场景包模型

一个场景包 = 配置 + 少量代码 + 种子数据，至少包含：

```
packs/customer_service/
  manifest.yaml        # 包元信息、依赖、启用开关
  agents/              # 代码 Agent 与提示词（可选）
  prompts/             # 路由与业务提示词
  tools/               # 领域工具实现（订单/退款/工单等）
  seeds/               # 演示数据、知识库文档、应答模板
  ui/                  # 场景文案：欢迎语、转人工提示、导航名称
```

约束：
- 内核不得 import 任何 `packs/` 下的模块；由包加载器反向注册。
- 场景包可以依赖平台能力，平台不能依赖场景包。
- 包内数据（工单、订单工具）不进核心 schema。

## 7. 交付与商业模式

### 7.1 版本划分

| 版本 | 内容 | 收费 |
|---|---|---|
| 社区版 | 平台内核 + 客服包 + IT Helpdesk 包，Docker 自部署 | 免费 |
| 企业版 | SSO、RBAC、审计增强、评测与回归、多工作区、白标 | 年度授权 |
| 服务 | 部署实施、场景包定制、培训、模型调优 | 按项目 |

### 7.2 许可建议

- 核心采用 Apache-2.0：最大化采用与传播。
- 企业版功能放在独立私有目录或私有仓库，采用商业许可。
- 若担心云厂商直接托管转售，可评估 AGPL 或 BSL；但会降低企业采用意愿，需权衡。

### 7.3 定价原则

- 私有化按"实例 + 年度"授权，不按 token 加价（客户自备模型 Key）。
- 实施服务单独计价，避免用低价授权补贴重交付。
- 企业版功能只卖"组织级能力"（权限、审计、SSO、评测），不锁基础对话能力。

## 8. 竞争与差异化

| 对比对象 | 它们强在 | 我们不打 |
|---|---|---|
| Dify / Coze / 大厂 Agent 平台 | 零代码搭建、插件生态、流量 | 不做通用编排画布与插件市场 |
| 传统客服 SaaS | 坐席、工单、呼叫中心全流程 | 不替代工单系统，做 AI 入口与工具对接 |
| 开源 RAG 项目 | 文档问答轻量 | 不止于 RAG，强调路由、工具、记忆、可观测 |

我们的差异化只有一条：**对话型业务 Agent 的运营闭环 + 可私有化**。具体是可追踪、可记忆、可维护、可替换场景包。

## 9. 明确不做什么（12 个月内）

- 通用 DAG 可视化编排。
- 计费系统与自助订阅。
- 多租户 SaaS 隔离（先单实例单租户）。
- 插件市场与移动端 App。
- 自研模型、向量库或工单全流程。
- 为单个客户 fork 代码；只允许配置与场景包定制。

## 10. 阶段目标与指标

| 阶段 | 目标 | 衡量 |
|---|---|---|
| 0–3 个月 | v0.1 开源发布 | 10 个真实部署、3 个外部 issue、1 篇社区转载 |
| 3–6 个月 | 第二个场景包可用 | IT Helpdesk 包被实际使用，抽象经受验证 |
| 6–12 个月 | 首个付费意向 | 企业版首单或首个实施服务合同 |
| 12 个月后 | 路径决策 | SaaS 化或继续开源 + 服务，二选一 |

注意：v0.1 阶段不看收入，看**真实部署与留存**。Star 数只作传播参考。
